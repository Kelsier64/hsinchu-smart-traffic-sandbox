# 容量感知策略篩選規格

狀態：規格與獨立函式已實作，單元測試已執行；所有容量／需求例子為**假設情境，非實測成效**。沒有新竹市區容量、完整替代路網、交通均衡或分流改善證據。

## 資料契約

候選路徑為已核對方向、起迄、連通與轉向限制的有向路段序列；每段只出現一次。傳入共同區間（明確起訖及時區）及`vehicles/interval`，背景流量B、有效容量C、可分流車輛數D、採納率p、預設負載門檻β。容量需具來源、適用車種及號誌／瓶頸條件；車種不一致時須先使用有來源的換算，不能直接相加。每段提供allowed、available、trusted；不明或過期等資料在上游轉成false／未知，不能悄悄當正常。

程式`screen_route`是一條完整路徑的篩選器，呼叫者以`route_verified=True`明確承擔方向、連通、轉向及起迄核對。它不會根據道路名稱推論連通性。`interval`需由呼叫者完成有效日期／時區解析，本函式要求非空且每段一致。D為區間內可推薦的整數車數，不是全縣車輛總數。

## 可查核規則

1. 預計新增車流Δ = N × p；N為收到建議的車輛數，上限D。採納率是情境參數，不是實測值；0採納率表示建議不產生新增流量，並非有效改善。
2. 對每段檢查`B + Δ ≤ βC`；路徑可用餘裕`S = min(βC - B)`。
3. 已禁行者排除；任一背景負載已高於βC者排除，即使D=0也不把路徑標為可新增流量。
4. p>0時`N = min(D, floor(S/p))`；N<D回傳limited，其餘eligible；p=0時Δ=0。β=.85只是示範預設，不是實測安全容量或道路管理規範，實地前須由場域固定。
5. 容量／背景未知、路徑／限制未驗證、資料不可用／不可信或區間／單位不一致，回傳insufficient_data；不放行。負值、NaN、無限值、採納率超界、零容量、非整數需求等拋出ValueError。
6. 回傳原因、N、Δ、各段負載及共同區間，保留輸入供管理者查核。不產生節省時間、減碳或全網總延誤數字。

同一情境分配多條路徑時，必須先扣除共享路段已分配餘裕、記錄未分配需求，再進行下一條；當前函式沒有多路徑最佳化。固定旅行時間排序、不分流、容量篩選可作策略設計比較，但旅行時間需由校準交通模型重新計算，不能使用固定時間聲稱分流有效。

## 假設範例

同一區間C=200輛、B=120輛、D=100輛，β=.85。p=.5時可建議100輛、預計新增50輛；p=1時上限50輛。兩情境負載均不超過.85。這僅說明限制數量如何計算，沒有實測道路名稱或效益。

測試命令：`python -m unittest discover -s tests -v`。測試涵蓋零需求、零／滿採納率、容量不足、未知資料、單位／時段不一致、非法輸入、禁行、未核對路徑、瓶頸與取整。
